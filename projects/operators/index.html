Which neural operator, for which data?

Five families of operator-learning models, each in its original form and in a newer variant that fixes a known weakness, are trained under one protocol on six standard PDE benchmarks. The goal is to explain which properties of the data favour which architecture, using these runs alongside published comparisons. Code on GitHub.

The ten models

Each newer variant changes one part of its base model. Comparing each pair shows whether that change helps on a given kind of data.

Six tasks

Each task isolates one property of the data. Five use the public FNO and Geo-FNO benchmark files that published results are reported on. The advection task is generated from its exact solution.

What the results say

Each finding below pairs our numbers with the property of the data behind them, and the published work that explains or disagrees with it.

1

On a regular grid, the Fourier models win, and they need far less data

FNO, the local-kernel FNO and KANO had the lowest error on every task with a grid: Burgers, advection, Darcy, Navier–Stokes and the airfoil's computational mesh. On Burgers they were 10–15× more accurate than the DeepONet family and the transformers. With only 100 training samples, FNO still reached 1.3%, while DeepONet was at 16% and Transolver at 20%.

Why. An FNO layer is a convolution done in Fourier space, so it assumes the answer depends on relative position, which holds for PDEs with constant coefficients on periodic domains. When the solution is smooth, a few Fourier modes carry almost all of it, and FNO works directly with those modes. DeepONet and the transformers have to learn translation structure from examples. That costs data, and it shows most when data is scarce.

2

Moving discontinuities break DeepONet, as theory predicts

On advected square waves, the Fourier models had 0.8% error and the DeepONet family 18–21%. More data barely helps DeepONet: 33% at 100 samples and 18% at 1000, while FNO went from 5% to 0.8%. In Lanthaler et al.'s own metric (median L1), FNO reproduced their result (0.96% vs 0.71%). Shift-DeepONet beat DeepONet (14.1% vs 16.8%), but by much less than their 2.8% vs 8.0%. They tuned each model, while we used one shared configuration, and a paper-faithful shared-trunk variant did no better.

Why. DeepONet's output is a weighted sum of p fixed basis functions. A square wave that can sit anywhere with any width is not close to any low-dimensional linear space, so the error falls slowly no matter how the weights are trained. That is Lanthaler et al.'s lower bound. Advection is also exactly a Fourier multiplier, a phase shift on each mode, which is FNO's native operation.

3

Unstructured point clouds belong to the transformers

On elasticity (972 scattered points), FNO, the local-kernel FNO and KANO cannot run at all. Transolver reached 1.05% and Transolver++ 1.44%, 5–8× better than the DeepONet family (5.2–8.7%).

Why. Transolver groups points into learned "slices" by their physical state rather than by grid location, and attention works on those slices, so it needs no grid. The DeepONet branch reads the point coordinates as one flat vector and has no notion of which points are neighbours. On the airfoil, where the mesh is structured, FNO on the mesh's index grid was best (0.62%). Grid methods recover once the geometry has a consistent indexing.

4

Letting the basis move helps on meshes and flows

Shift-DeepONet halved DeepONet's error on the airfoil (0.98% vs 1.99%), nearly halved it on Burgers (1.6% vs 2.9%), and cut it on Navier–Stokes (23% vs 33%). On Darcy, where nothing moves, it made no difference (4.4% vs 4.5%).

Why. The input-dependent shift lets a basis function follow a feature, such as a shock on the airfoil or a front in Burgers, as it changes position from one input to the next. When the solution's features are pinned in place, as in Darcy's fixed domain, there is nothing to shift.

5

DeepONet shrugs off noise; the transformers and local kernels do not

With 5% noise on the inputs, the DeepONet family's error barely moved (advection: 18.4% to 18.7%). FNO and KANO degraded gently (0.8% to 3.2%), the local-kernel FNO more (0.8% to 7.5%), and Transolver the most (6.1% to 33%). We did not see the catastrophic FNO failure Lu et al. report (0.66% to 270% at 0.1% noise), which was measured on a 40-point grid.

Why. DeepONet's branch compresses the input to a small feature vector, which averages out noise, and its error is dominated by its representation limit anyway. FNO truncates to low Fourier modes, which filters most white noise. A finite-difference kernel amplifies high-frequency noise, much as a numerical derivative does. Transolver assigns points to slices pointwise, so noisy values can move points into the wrong slice.

6

"Discretization-invariant" has limits

Trained at one resolution and tested at others, the DeepONet family was exactly flat, since its branch always reads the same sensors and its trunk can be queried anywhere. The transformers stayed within about 1.5× of their error on the training grid. KANO was flat on Darcy and rose 4× at the finest Burgers grid. FNO held up to 2× finer grids, then degraded at 4× (Burgers: 0.23% to 3.7%). The local-kernel FNO broke on finer grids: 0.17% to 19% on Burgers at 4096 points, and 1.5% to 23% on Darcy at 211 × 211.

Why. We traced the local-kernel failure to its finite-difference branch, using the trained models without retraining:

Other explanations were ruled out. Giving the model band-limited inputs, with no detail beyond what the training grid could hold, changed nothing, so the fine-scale content is generated inside the network. Recomputing the local integral (DISCO) kernels for the finer grid also changed nothing. The finite-difference output grows layer by layer on the finer grid (Burgers at 4096 points: 0.009, 0.16, 0.41, 0.77 across the four layers, against about 0.002 at the training resolution). The pointwise nonlinearities create detail finer than the training grid could represent. A derivative stencil amplifies detail at wavenumber k by about k, and the next layer feeds it back in. On the training grid this detail is capped by the grid spacing, so the model never learned to suppress it. Filtering the stencil's input to the training band restores most of the accuracy, a simple fix at inference time. Plain FNO has no derivative branch and degrades more mildly at 4096 points (3.7%). The likely cause is the same nonlinearities creating content above the retained Fourier modes, though we did not test it directly. This fits Shikhman (2026), who found in-distribution accuracy a poor predictor of robustness to resolution shift.

7

KANs: the architecture matters more than the activation

DeepOKAN, which swaps DeepONet's MLPs for radial-basis KANs, was worse than DeepONet on Burgers, advection and Darcy, and better on Navier–Stokes, airfoil and elasticity (5.2% vs 7.1%), at 2–9× the parameters. It was never the best model on any task. KANO performed about as well as FNO, the best by a small margin on advection, Darcy and Navier–Stokes (9.5% vs 11.2%), at 3× the parameters and 4–10× the training time of FNO.

Why. DeepOKAN keeps DeepONet's linear reconstruction, so it inherits the same limit, and learnable activations do not change it. KANO keeps FNO's Fourier structure and adds position-dependent terms, so it inherits FNO's strengths. Its largest margin over FNO was on Navier–Stokes.

8

Transformers need training budget; FNO does not

With the same epoch budget, the transformers trained 5–25× longer than FNO per run and were still improving when training stopped. On Navier–Stokes they reached 34% and 47%, against 7–9% published after 500 epochs with smaller batches. Our FNO, trained with the same budget, came close to or beat its published numbers (Darcy 1.4% vs 1.1%; Navier–Stokes 11% vs 16%).

Why. FNO's strong assumptions leave little to learn, so it converges fast. Transolver has to discover its slice structure from data, which takes more optimisation steps. Under a fixed compute budget, that matters as much as final accuracy. This finding is about the budget, not the ceiling; the published results show what these models reach with more training.

Physics-informed networks: no data, one instance at a time

PINN and PirateNet fit a network to a single PDE instance using only the equation, the initial condition and the boundary conditions. They need no training data, but every new input requires a new optimisation. The table compares them on three test instances per task with the operators' error on the full test set, and the time per instance.

Running.

Smooth problems. On Burgers, PirateNet reached 0.08%, more accurate than every trained operator, and the plain PINN reached 0.43%. With the equation known exactly and a smooth solution, fitting one instance directly has no generalisation gap to pay. PirateNet's additions (Fourier features, identity-initialised residual blocks and causal weighting) cut the error by about 5× over the plain PINN.

Discontinuities. On advection, the plain PINN reached 29%, and PirateNet diverged (179%). At a jump the PDE residual is effectively infinite, so the residual-based causal weights never let training move past the first instants, and the smooth tanh network cannot represent the jump anyway. Darcy's piecewise-constant coefficient caused the same trouble in milder form: 22% for PINN and 11% for PirateNet (between 2.5% and 24% across instances), against 1.4% for the operators. This matches the known failure modes of PINNs on transport and on problems with sharp features (Krishnapriyan et al., NeurIPS 2021).

Cost. Each PINN solve took 1–6 minutes on the GPU, while a trained operator answers a new instance in about a millisecond. PINNs make sense when there is no training data or only a few instances to solve; operators make sense for many queries.

They prove that models which build the output as a weighted sum of fixed basis functions, as DeepONet does, need rapidly more basis functions to represent a moving jump. FNO and Shift-DeepONet build the output nonlinearly, which avoids this limit.

These two sets of results look inconsistent for DeepONet on advection: 0.22% against 7.95%. The grids differ. At 40 points a jump spans one or two cells, while at 2048 points with narrower waves it is sharp. The advection task here uses 1024 points to test this directly.

Protocol and caveats

  • Every data-driven model gets the same loss (relative L2), optimiser (AdamW with a one-cycle schedule), normalisation and epoch budget per task: 300 epochs for the 1D tasks and elasticity, 100 for Darcy and airfoil, 200 for Navier–Stokes. The published numbers used 500 epochs, so absolute errors here run higher. The comparison between models is like for like.
  • Navier–Stokes is trained on randomly placed one-step windows (10 frames to the next) to fit a 12 GB laptop GPU. It is tested on the full 10-step rollout, which is the published metric.
  • KANO is adapted. The reference code is single-channel and 1D, with memory growing as N³. The version here evaluates the same kind of operator (a position-dependent Fourier multiplier followed by a spline KAN) using separable symbols and FFTs, with lifting layers so it can run on 2D tasks.
  • FNO, local-kernel FNO and KANO need a grid, so they are not run on the elasticity point cloud. Published work runs FNO there only through geometry-mapping extensions.
  • PINN and PirateNet solve one PDE instance at a time without training data, so they are reported separately, by error against compute per instance.
  • Each run uses one seed. Differences of a few percent between models should not be over-read.
